# flux-infra


> [!NOTE]
> As of 9/11/26 this is mostly out of date as I've pivoted off of FluxCD and switch to ArgoCD, may archive this or use the same structure for my proxmox cluster


A FluxCD-managed K3s cluster running on the Oracle Cloud free tier. One master node for now. Nodes are addressed over Tailscale, so adding nodes in other regions later should mostly be a matter of joining them to the tailnet.

This is a homelab, not production. I use it to keep GitOps patterns fresh and to try things before I'd want to try them at work.

## What's running (outdated)

- **Flux CD** (source, kustomize, and image controllers) syncing this repo every 10 minutes
- **podinfo** as a HelmRelease, standing in for a real workload
- **[capacitor-ui](https://github.com/gimlet-io/capacitor)** pulled from OCI (`ghcr.io/gimlet-io/capacitor-manifests`) into `flux-system`, so I can see Flux state without the CLI

![Cluster diagram](https://raw.githubusercontent.com/david-shepard/flux-infra/refs/heads/main/kubediagram.png)

The diagram is regenerated by a workflow using [KubeDiagrams](https://github.com/philippemerle/KubeDiagrams).

## Layout

```
clusters/dev/     # what the Oracle cluster points at: infra first, then apps
apps/base/        # app definitions
apps/dev/         # dev overlays on top of base
scripts/          # validate.sh, adapted from fluxcd/flux2-kustomize-helm-example
```

Infra reconciles before apps. Anything environment-specific is an overlay rather than a fork of the base.

## CI

`kustomize-verify` runs `scripts/validate.sh` on every push to main. It pulls the Flux OpenAPI schemas and runs kubeconform against the custom resources and every kustomize overlay, so a manifest that won't build gets caught before Flux tries to apply it. There's also a Tailscale workflow for reaching the cluster from Actions, and the KubeDiagrams job.

## Security notes

I went through this repo after reading [Wiz's writeup on GitHub PAT attacks](https://www.wiz.io/blog/github-attacks-pat-control-plane), since a homelab repo with cluster access is exactly the shape of thing they describe. What changed:

- Dropped the `secrets.PAT` fallback in the KubeDiagrams workflow. It's `GITHUB_TOKEN` now, which is repo-scoped and expires with the run.
- Pinned actions to commit SHAs instead of tags. The tj-actions/changed-files compromise (CVE-2025-30066) is the reason tags aren't good enough.
- Added Gitleaks and Dependabot.
- Explicit `permissions:` blocks on workflows, read-only unless a job needs more.

Three actions still float on `main` or a tag because they have no SHA-pinned releases I trust more: KubeDiagrams, the Flux action, and the Claude Code action. Each is marked with a TODO in the workflow.

The kubeconfig is still a GitHub secret, which I'm not happy about. The right fix is short-lived credentials rather than a long-lived kubeconfig that's painful to rotate. Haven't gotten to it.

See [SECURITY.md](SECURITY.md) for the full writeup.

## Running it yourself

Fork it, then bootstrap Flux against your fork:

```bash
flux bootstrap github \
  --owner <your-username> \
  --repository <your-repo> \
  --private-key-file /path/to/ssh/key \
  --personal
```

Then `flux get kustomizations` to watch it reconcile. You'll want your own cluster, and the Oracle free tier ARM shape (2 OCPU, 12GB) is what everything here is sized for.

Before pushing a manifest change, run `./scripts/validate.sh` locally. It's the same check CI runs.
